### The "Expression" problem
    - OO languages can add new data types (just add a new class)
      but it's harder adding new operations
        - because to add an operation that works on a variety of
          classes you have to add an implementation for every
          class
    - functional languages are the other way around.
        - It's harder adding new data types, because you
          have to change existing function definitions to accept
          a new datatype
    - traditionally LISPs use a "multimethod" which provide a way
      to dispatch functions arbitrarily

### "STM": software transactional Memory
    - facilitates safe sharing of data between threads
    - also: safe way to implement state with mutable objects
    - simplest STM construct: atoms
        - synchronous transactional access to single values
        - $MY_IMAGES/cs/clojure/atom-reset-basics.jpg
    - gotcha: don't use `reset!` to set values according to the
      current value of the atom
        - example: count to 1000 using a loop
            - but look, at the end of the loop, count isn't 1000!
            - because 35 times, between dereferencing count and
              setting the new value, some future ran and set it
              to a different value
                - $MY_IMAGES/cs/clojure/dont-use-reset-1.jpg
        - solution: use `swap!`
            - use a function to update `count`
            - the functions get added to a _queue_ that gets
              called on count
            - so everything gets sychronised in the order they
              came in, and exactly as many times as there are
              functions called
                - $MY_IMAGES/cs/clojure/dont-use-reset-2.jpg
            - note: swap can take more arguments
                - $MY_IMAGES/cs/clojure/dont-use-reset-3.jpg
        - atoms can have a validator
            - if you try to "swap" a string value into an atom
              with an `integer?` validator, then you get a JAVA
              exception
            - $MY_IMAGES/cs/clojure/atom-validator.jpg

### Recur / tail calls
    - Clojure has no AUTOMATIC tail call optimisation due to
      limitations of the JVM.
    - Hence must explicitly use the 'recur' special form.
    - 'recur' really forces the same stack frame to be reused
    - to prevent infinite recursion, 'recur' should be used
      within a conditional form
    - 'recur' must be in the tail position of the function
    - can be 'transitively' in tail position: this means an "if"
      form is in tail position, and "recur" is inside the "if",
      so recur is transitively in tail position.
    - recur in nested functions: a recur form invokes the
      function in which it is most directly contained
        - inside a nested function, we cannot use 'recur' to
          invoke an enclosing function
        - loop: establishes a "recursion point" for a recur form.
            - A 'recur' form in tail position of a loop body
              jumps execution back to the start of the loop, with
              new values bound to the symbols
        - loop and recur allow us to repeatedly iterate over
          a body of code  without creating one-off functions just
          for the sake of looping
            - less verbose with loop:
                - $MY_IMAGES/cs/clojure/loop-recur-01.jpg
            - more verbose as a function:
                - $MY_IMAGES/cs/clojure/loop-recur-02.jpg

### Nice questions: symbols / vars
    - See: $MY_CODE/clojure/symbols-vars.clj
    - (aside: I asked myself: "Can two symbols refer to the same
      var? YES! This was answered below...")
        - later: NO! Someone said you would still have two
          different var containers if you had 2 symbols
    - To evaluate a `symbol`, first the corresponding `var` must
      be looked up, then the `var` must be DEREFERENCED.
    - Why does Clojure work this way? What benefit could there be
      from such a design?
    - I understand that vars have certain special properties
      (they can be private, or const, or dynamic...), but
      couldn't those properties simply be applied to the symbol
      itself?
    - Answer: Symbols are names
        - Unlike most programming languages, Clojure makes
          a distinction between things and the names of things.
          In most languages, if I say something like var x = 1,
          then it is correct and complete to say "x is 1" or "the
          value of x is 1".
        - But in Clojure, if I say (def x 1), I've done two
          things:
            - I've created a Var (a value-holding entity) ...
            - and I've named it with the symbol x.
            - Saying "the value of x is 1" doesn't quite tell the
              whole story in Clojure. A more accurate (although
              cumbersome) statement would be "the value of the
              var named by the symbol x is 1".
        - Symbols themselves are just names, while vars are the
          value-carrying entities and don't themselves have
          names.
        - If extend the earlier example and say `(def y x)`,
          I haven't created a new var, I've just given my
          existing var a second name. The two symbols x and y are
          both names for the same var, which has the value of 1.
    - full discussion:
        - $MY_NOTES/cs/lisp/clojure/why-symbols-vars.txt
    - another reason: (runtime update!)
        - $MY_NOTES/cs/lisp/clojure/brian-course.txt
        - functions can change after definition, because the
          function body may reference a _symbol_ 'foo' but the
          _var_ sitting behind this symbol may change later
        - arguably this affects 'functional purity'
        - the reason Clojure does this, and the reason that
          namespaces map symbols to vars, instead of mapping
          symbols directly to other values, is so your code can
          be _UPDATED AT RUNTIME_.

### lexical scope
    - A function’s parameter bindings have a lexical scope:
      they’re visible only inside the function body.
    - Functions are not the only way to create a lexical binding.
    - The special form `let` does nothing other than create a set
      of lexical bindings:
        - `(let [bindings*] exprs*)`
    - The bindings are in effect for `exprs`, and the value
      of the `let` is the value of the _last expression_ in
      `exprs`.

### Namespaces
    - Namespaces organise and control access to 'vars'.
    - When we created a var with `def` or `defn`, it is created
      in the default REPL namespace: “user”
    - You can create your own namespace and switch to it using
      `ns`. Any vars created will now be created in this
      namespace.
    - Let’s create a new namespace now.
        - (ns alice.favfoods)
    - In Clojure, a namespace is a collection of `names`
      (symbols) that refer to `vars`. Each var is bound to
      a value.

### Symbol var function
    - or better: symbol (name) -> var -> function
    - summary:
    - ((deref (resolve '+)) 2 3)

    - https://stackoverflow.com/questions/9113387/difference-between-symbols-and-vars-in-clojure
    - `+` is a symbol sitting in `clojure.core` which is by
      default accessible to your code.
    - When used in your code (without any very advanced intents
      such as quoting it or finding out its class) ― clojure will
      seek the Var which it points to.
    - If this `Var` is a function, when `+` is used in head
      position of a list, clojure will try to call that function
      (you get NullPointerException if this Var happened not to
      point at a function).
    - If supplied as an argument to another function, that
      function may do the same to call it. That's how function
      calling works.

    - Most or all languages use symbol tables. Being a somewhat
      dynamic language, Clojure uses this extra layer of
      indirection (Symbol → Var → function, rather than only
      Symbol → function) so that dynamically rewriting which
      function is tied to which symbol ― is more feasible and
      elegant, and this is sometimes a source of curiosity for
      beginners.

    - As other answers have somewhat overly emphasized, you may
      otherwise perform fancy stuff like quote it ('+) to avoid
      its evaluation, or even inspect it with class and/or
      resolve as if you are interested in verifying what it is
      (class), or which namespace it sits in (resolve).
    - You can also poke at the `var` it points at via `var` or
      `#'`. You'll typically do those fancy things if you are
      writing macros or if you're very experimentally inclined,
      especially when working in the REPL; depending on which
      style you write your macros, you might actually quote a lot
      in them.
