    - But for me the fundamental advantage of data is:
    - Bringing data makes it easy to test and verify assumptions.

      gaps.

    - Answer: I dunno.
    - Data can easily miss a whole lot of subtlety. Subject
      knowledge, theory, and intuition can capture much more of
      that subtlety, at the cost of being more vulnerable to
      bias.
    - Making decisions purely based on data misses out a lot. And
      can still lead to bias, not caused by the decision maker,
      but by the data gathering process.
    - In my mind, data exists to detect bias, and illuminate
      interesting phenomena. But decisions should ultimately be
      based on in depth knowledge and theory. And leeway should
      be given for those to be somewhat misaligned to data.

### HEP Physics talk: "histo-grammer"
    - http://histogrammar.org/
    - "Expressing complex data aggregations with Histogrammar"
      Jim Pivarski
    - https://www.youtube.com/watch?v=mB4Chl0ly-g
    - R, Numpy, Pandas, Pyspark: histogram API's require _all_ of
      the input data before giving you a histogram
    - HEP Root: treat histograms as fillable containers.
    - HEP software: the API assumes the dataset is too big for
      a single function call. So it's intrinsically single-pass
      (it can't pre-scan to set bin width or range.)
    - the aggregators must be "linear monoids"

    - HEP pseudo code:
        ```
        h = Histogram (numBins, lowEdge, highEdge)
        for x in data:
            h.fill(x)
        h.plot()
        ```

### "Hive" versus "Impala"
    - "ETL" - Extract, Transform, Load
    - "MPP" - Massively Parallel processing

    - Hive: transforms SQL queries into MapReduce or Apache
      Spark jobs under the hood; great for long-running
      _ETL_ jobs.

    - Impala, is basically an _MPP_ analytic database on top
      of Hadoop largely written in C++ for speed: pushes
      data processing down to local DataNodes, avoiding
      network bottlenecks.

### RDBMS vs MapReduce 1
    - RDBMS:
        - key ideas: relational algebra, physical/logical data
          independence, indexing

    - MapReduce:
        - key ideas: fault tolerance, no loading, direct
          programming on 'in situ' data (don't bother defining
          a schema)

### RDBMS vs MapReduce 2
    mapreduce is catching up to RDBMS!

    * traditional RDBMS features
        - declarative query language         Pig, Hive
        - schemas                            Hive, pig dryad
        - logical data independence (views)
        - caching/materialised views
        - indexing                           Hbase
        - algebraic optimisation             Pig (dryad, Hive)
        - ACID/transactions

    * MapReduce features
        - high scalability (1000s of machines)
        - fault tolerance (traditional RDBMS good at recovery)
        - "one person deployment"

### differences Hadoop and SPARK
    - Two high level differences:
        1. Spark stores data _in-memory_ whereas Hadoop stores on
        disk.
        2. Spark's data storage model, resilient distributed
        datasets (RDD), uses a clever way of guaranteeing fault
        tolerance that minimizes network I/O.

    Spark academic paper:
        > "RDDs achieve fault tolerance through a notion of
        > lineage: if a partition of an RDD is lost, the RDD has
        > enough information about how it was derived from other
        > RDDs to be able to rebuild just that partition."

    - Therefore replication not needed for fault tolerance.
    - (Hadoop uses replication to achieve fault tolerance)


### Apache Spark
    * improved version of map reduce
    * if you have _legacy_ SQL queries you can run them
      unmodified on spark dataframes in the cloud

### difference MapReduce and MPI
    - For MapReduce, MPI doesn't make sense because it's not
      reliable: if one process dies, the whole job dies.
    - This is the main reason MPI is not a great base for
      MapReduce. MPI is for tightly coupled apps on fast,
      reliable networks (supercomputers), while MapReduce is
      designed for running embarrassingly parallel workloads on
      slow, unreliable hardware

### HBASE
    * a NOSQL _random access_ database built on top of HDFS
    * basically a way to query a large amount of files
      stored on HDFS in a random like and simple way

### ACID
    * (A)tomicity   - all parts of a transaction succeed or fail together
    * (C)onsistency - database state is consistent
    * (I)solation   - no transaction affects any others (acomplished through locking)
    * (D)urability  - once a transaction is comitted it wont be lost
