### window functions

    Ranking functions  SQL                  DataFrame API
                       ---                  -------------
                       rank                 rank
                       dense_rank           denseRank
                       percent_rank         percentRank
                       ntile                ntile
                       row_number           rowNumber



    Analytic functions  SQL                  DataFrame API
                        ---                  -------------
                        cume_dist            cumeDist
                        first_value          firstValue
                        last_value           lastValue
                        lag                  lag
                        lead                 lead

    Once a function is marked as a window function, the next
    key step is to define the Window Specification
    associated with this function. A window specification
    defines which rows are included in the frame associated
    with a given input row. A window specification includes
    three parts:

    - _Partitioning Specification_: controls which rows will
      be in the same partition with the given row. Also, the
      user might want to make sure all rows having the same
      value for  the category column are collected to the
      same machine before ordering and calculating the
      frame.  If no partitioning specification is given,
      then all data must be collected to a single machine.

    - _Ordering Specification_: controls the way that rows
      in a partition are ordered, determining the position
      of the given row in its partition.

    - _Frame Specification_ (OPTIONAL?): states which rows
      will be included in the frame for the current input
      row, based on their relative position to the current
      row.  For example, “the three rows preceding the
      current row to the current row” describes a frame
      including the current input row and three rows
      appearing before the current row.

### spark <-> hive integration
    - SparkSQL gets shipped with its _own metastore (derby)_,
      so that it can work even if hive is not installed on
      the system. This is the _default_ mode.

    - In the above question, you created a table in hive.
      You get the table not found error because SparkSQL is
      using its default metastore which doesn't have
      metadata of your hive table.

    - If you want SparkSQL to use the hive metastore instead
      and access hive tables, then you have to add
      hive-site.xml in spark conf folder.

### Chris Webster  Advice
    "Spark In Action" from Manning is the best all-round book on
    Spark that I've seen, and it's fairly up to date (Spark
    2.x):

    https://www.manning.com/books/spark-in-action

    There are a couple of O'Reilly books that are a bit older so
    some of their contents are obsolete.

    "Learning Spark" (2013) is pretty good on the basics of how
    Spark works, and also has useful information on some of the
    painful configuration stuff. But it's quite old now e.g.
    limited coverage of Data Frames, and nothing on Data Sets.

    http://shop.oreilly.com/product/0636920028512.do

    "Advanced Analytics With Spark" (2015) is more recent and
    focuses mainly on machine learning with various practical
    examples:

    http://shop.oreilly.com/product/0636920035091.do

    O'Reilly are also promoting a new book "Spark: The
    Definitive Guide" but it's not out yet, although some
    chapters are available to download:

    http://shop.oreilly.com/product/0636920034957.do

    On PySpark vs. Scala Spark:

    DataBricks has some decent documentation which includes
    stuff on moving from Python to PySpark, although some of
    their docs are specific to their proprietary
    Spark-as-a-platform product:

    https://docs.databricks.com/index.html

    One big problem with Python/Scala on Spark in general is
    that the Scala API is more comprehensive than Python, so
    there are things you can do in Scala with Spark that you
    can't do in Python.

    Another common problem that I've seen is that people really
    struggle to adapt their thinking from the single-machine
    classic Python mode (numpy, pandas, scikit-learn etc) to the
    fundamentally different distributed model of Spark.

    People keep trying to work with Python dicts, lists and
    arrays instead of Spark's RDDs and Data Frames/Sets. This
    forces data to be collected onto single nodes instead of
    being distributed, eliminating the key benefit of Spark and
    often killing your program when the RAM is used up.

    So the best thing you can do if you're learning PySpark is
    learn the basics of *Spark* first: learn about why Spark
    uses the distributed model, how it does it, how Spark uses
    functional programming patterns (map etc) to do things
    instead of loops, what the core data structures are (RDDs,
    Data Frames, Data Sets), and how to use the incredibly rich
    APIs offered by these data structures.

    Understand Spark, and you'll find it much easier to write
    proper programs in PySpark.

    Or learn Scala and enjoy the full power of Spark!
