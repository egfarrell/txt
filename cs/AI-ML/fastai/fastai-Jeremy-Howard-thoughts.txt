# Notes on fastai coding style
    - Fastai's code style is inspired by 60 years of APL/J/K
      programming and Jeremy's 25-year experience in language
      design.
    - It's tailored for scientific programming and experimental
      development.
    - Many have strong coding style opinions; but experienced
      coders understand multiple valid approaches. The Python
      community's strong views may stem from its
      beginner-friendly nature. But when contributing to fastai:
      - Don't alter existing code to reduce style compliance;
        avoid auto-linters.
      - Ensure your code somewhat aligns with the surrounding
        code.
    - I hope you see value in this style guide when contributing.
    - My style perspective is heavily influenced by Iverson's
      1979 Turing Award lecture, "Notation as a Tool For
      Thought". Read it if possible; it's seminal.
      - It posits that programming languages can merge with
        mathematical notation benefits.
      - Brevity aids reasoning, not just terseness, as discussed
        in a Hacker News thread.
      - This style fosters expository programming, especially
        with tools like Jupyter Notebook.
      - World-class programmers, like Arthur Whitney, often adopt
        this style.

### Layout
    - Code width should be about 160 characters.
    - Each code line should convey one idea.
    - If possible, combine if-statement and its action using `:`.
    - Use ternary operators for brevity, e.g., `x = y if a else b`.
    - Place 1-line function body with the `def` line using `:`.
    - Group similar 1-line functions without gaps.
      - Examples:
        - `def det_lighting(b, c): return lambda x: lighting(x, b, c)`
        - `def det_rotate(deg): return lambda x: rotate_cv(x, deg)`
        - `def det_zoom(zoom): return lambda x: zoom_cv(x, zoom)`
    - Align similar statement parts for clarity.
    - Group class member initializers using destructuring assignment.
      - Example: `self.sz,self.denorm,self.norm,self.sz_y = sz,denorm,normalizer,sz_y`
    - Minimize vertical space. Import multiple modules in one line.
    - Use 4-space indentation.
    - Add spaces around operators based on domain-specific notation.
    - No trailing whitespace.

### Style guide
    - Some Python features enable concise coding. e.g.
        - list comprehensions,
        - lambda functions,
        - format strings, and
        - numpy array programming
    - Aim to encapsulate key ideas of a concept in one screen;
      avoid excessive scrolling.

### Symbol naming
    - Adhere to Python casing: CamelCase for classes, under_score
      for others.
    - Follow the Huffman Coding principle: commonly used terms
      should be shorter.
    - Refer to `abbr.md` for abbreviation guidelines.
    - Examples:
      - Use `sz` for size, `img` for image, `lm` for language
        model.
      - Use `o` for objects, `i` for index, `k` and `v` for
        dictionary keys/values.
      - `x` for tensor inputs, unless other standards apply.
    - Match the naming patterns in the existing code, e.g., `det`
      for deterministic.
    - Use domain-specific abbreviations: `kl_divergence` over
      `kullback_leibler_divergence`.
    - Align with paper nomenclature unless it contradicts common
      conventions.
    - Research suggests overly long symbol names can hinder code
      comprehension.

### Algorithms
    - Ensure fast, accurate, concise algorithm implementation.
      Optimize with profiler if over _1-second_ run time.
    - Ensure scalability within `16GB RAM`.
      - Use lazy structures like generators.
    - Comment with equation numbers from papers.
    - Prefer numpy/pytorch broadcasting and advanced indexing.
    - Test latest paper implementations on datasets before PR.
      - Include notebook gist link in PR.

### Other Stuff
    - Assume latest python and libraries; flag recent
      dependencies. Avoid beta versions.
    - Limit comments; clarify with clear code and symbol names.
    - Link external sources in code.
    - Use `import *` for comprehensive module imports; define
      `__all__`.
    - Assume user's editor proficiency.
    - Avoid auto-linters/formatters.
    - Keep PRs concise; discuss complex issues in forums.

### Documentation
    - Main documentation in `docs_src` notebooks.
    - In code, one-line docstring with main parameter references.
    - Model after Python's `re` module for documentation style.

### FAQ (PEP 8)
    - Why not PEP 8? Not ideal for our programming style.
    - Editor's PEP 8 issues? Disable linting in settings.
    - Concern about style repelling contributors? Style isn't rigid; open-mindedness valued.
