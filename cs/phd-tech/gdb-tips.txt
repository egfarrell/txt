### "w_powf.c: no such file or directory" !
    (c)gdb can't step into the 'libc' source

    solution 1:
        - don't STEP into the 'libc' code!
        - just hit "n" over it

    solution 2:
        - if you really need to step into the code:
            - first type: `info sources` on GDB command line
            - this lists where GDB expects the source to be
                - in my case it was `/build/glibc-t3gR2i`
            - download the libc source: `ai libc-source`
            - a tar file will be placed in '/usr/src/libc'
            - move source to wherever GDB expects it

### "x": eXamine memory
    - `(gdb)` x/14xb 0xbffff450

    - `(gdb)` x/{repeat}{format}{size} ADDRESS
    - `(gdb)` x/14       x       b     0xbffff450

    - {format}:           - {size}:
        - `o` octal         - `b` byte
        - `x` hex           - `h` halfword
        - `d` decimal       - `w` word   <-------- normally this one
        - `f` float         - `g` giant, 8 bytes
        - `a` address
        - `i` instruction

### _CGDB_: Reading from [STDIN]
    - Scenario: cgdb doesnt work with line `gets(buffer);`
    - This is a known limitation.
    - Theres 2 options for interactive console programs:

    1. Best option: Run program in another terminal and attach
       cgdb to it by passing the PID
          - This way the program has a terminal environment to
            itself and you don't have to worry about cgdb and
            your program sharing a terminal.

    2. Use the "_TTY_" window. This window ISNT a full-fledged
       terminal emulator, so wont properly support programs that
       use things like ncurses.
            - in the "top" window (command mode) press `T`
            - new TTY window appears...
            - press `I`      to enter TTY window
            - press `<ESC>`  to leave TTY window

### Supply program arguments

    - Option 1:
    - prefix executable name with `gdb --args`
     ```
        gdb --args myprog  --deep-dish  --toppings=pepperoni
        (gdb) show args
        " --deep-dish --toppings=pepperoni"
     ```

    - Option 2:
        - Use "set args". E.g. if you normally run like:
          `myprog  -paramater1   -parameter2`
        - then do:
          `(gdb) set args  -parameter1  -parameter2`


### Show frames / call stack
    - `bt` (backtrace)      display call stack.
    - `f`(rame) <args>      select a frame on the call stack for inspection
    - `info f`(rame) <args> info about specific frame on the stack. Without arguments, will display the current frame
    - `info locals`         info about local variables on the stack.


### view arguments passed to a function
    - clever:
    - jump up a frame and view from calling function. eg:
    - `(gdb) frame 8`
    - will put you in the frame of the caller.
    - Examine the arguments that are being passed.

### auto-load options
    1. You can add the line:
        `set auto-load safe-path /`

        - To your home directory’s `.gdbinit` file. This will
          override ALL security and GDB will ALWAYS open
          a .gdbinit file if it finds one.

        - If you are developing on your own machine, or a secure
          machine (however you would like to define that), then
          this is probably the quickest and easiest solution.

    2. If you want to be a little more careful, you can add the
       directories individually to your home directory’s .gdbinit
       file:
            `set auto-load safe-path /home/ef/repos/myproject`

        - Or you allow ALL sub-paths under your home directory
            `set auto-load safe-path /home/ef`

    3. Finally, you can pass a path in on start-up:
        `gdb -iex "set auto-load safe-path /path/to/.gdbinit/file"`

    4. If you want to see all the trusted paths, just type:
        `show auto-load safe-path`
